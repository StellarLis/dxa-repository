# Сервис ИИ по контролю качества денситометрических исследований

Сервис для автоматической оценки качества рентгеновских DXA-денситометрических исследований по DICOM-изображениям.

Система анализирует исследования поясничного отдела позвоночника и проксимального отдела бедренной кости, определяет анатомическую область, проверяет изображение по набору критериев качества и формирует структурированный результат с указанием выявленных нарушений.

---

## 1. Назначение системы

Денситометрические исследования используются для оценки минеральной плотности костной ткани. Достоверность измерений зависит в том числе от корректности укладки пациента, позиционирования исследуемой области, отсутствия артефактов и правильности определения области интереса.

Цель сервиса — автоматизировать первичный контроль качества исследования и выявлять типовые нарушения до этапа клинической интерпретации.

Методические требования предусматривают автоматическое определение анатомической области, классификацию исследования как качественного или содержащего нарушение, проверку позиционирования и областей измерения, а также формирование структурированного отчёта.

### Основные возможности

Сервис:

1. принимает DICOM-исследования без разметки;
2. определяет анатомическую область:
   - `spine` — поясничный отдел позвоночника;
   - `hip_left` — левое бедро;
   - `hip_right` — правое бедро;
3. определяет наличие нарушения качества;
4. определяет конкретный тип нарушения;
5. формирует человекочитаемый комментарий;
6. распознаёт наличие эндопротеза бедра;
7. обрабатывает отдельные файлы и пакет исследований;
8. предоставляет HTTP API и веб-интерфейс;
9. формирует итоговые результаты в формате XLSX/CSV.

Для DXA в текущем контуре область исследования определяется по классам spine, hip_left, hip_right. Отдельная классификация проекции как самостоятельного выходного поля не реализована; типичная проекция определяется в рамках соответствующей анатомической области.

## 2. Проверяемые критерии качества

Система реализует гибридный подход: в зависимости от природы конкретного критерия используется либо нейросетевая модель, либо алгоритм классической компьютерной геометрии.

### 2.1. Поясничный отдел позвоночника

Проверяются:

- корректность позиционирования;
- наклон оси позвоночника;
- наличие посторонних объектов и выраженных артефактов.

Для оси позвоночника используется критерий допустимого наклона до 5 градусов, соответствующий методическим требованиям.

Реализованные коды нарушений:

```text
incorrect_positioning
axis_tilt_over_5deg
foreign_object_or_artifact
```

### 2.2. Проксимальный отдел бедренной кости

Проверяются:

- корректность позиционирования;
- наличие необходимой анатомии;
- отсутствие неправильной ротации;
- корректность области интереса (ROI).

Методические критерии требуют визуализации большого вертела, шейки бедра и седалищной кости, а также оценки ротации и размеров области интереса.

Реализованные коды нарушений:

```text
rotation_error
roi_incorrect
```

### 2.3. Эндопротез

Сервис дополнительно определяет наличие эндопротеза.

Если эндопротез обнаружен, критерии `rotation_error` и `roi_incorrect` для данного изображения не применяются. Это является предусмотренной обработкой особого случая, а не ошибкой обработки.

## 3. Архитектура решения

Решение представляет собой гибридный pipeline, объединяющий:

- загрузку и нормализацию DICOM;
- определение анатомической области;
- нейросетевую классификацию;
- геометрический анализ;
- обработку особых случаев;
- агрегацию результатов;
- формирование структурированного результата.

### Выбор метода для каждого критерия

| Критерий | Область | Метод |
|---|---|---|
| `axis_tilt_over_5deg` | spine | геометрический анализ |
| `roi_incorrect` | hip | геометрический анализ |
| `incorrect_positioning` | spine | ResNet18, multi-label |
| `foreign_object_or_artifact` | spine | нейросетевая модель |
| `rotation_error` | hip | нейросетевая модель |
| `обнаружение эндопротеза` | hip | геометрический анализ |

Геометрические методы используются там, где критерий является преимущественно измерительным: например, для оценки угла наклона или расстояния до границы ROI.

Нейросетевые модели используются для распознавания визуальных признаков нарушения.

Пороговые значения геометрических и нейросетевых методов калибруются отдельно и проверяются на отложенных данных.

## 4. Системные требования

### Программные требования

- Python 3.11 или выше;
- Linux/Unix-совместимая система для контейнеризированного запуска;
- Docker — для запуска контейнеризированной версии.

Все основные зависимости проекта зафиксированы в:

```text
requirements.txt
```

Решение не требует подключения к внешним закрытым сервисам и рассчитано на локальную обработку медицинских изображений.

### Аппаратные требования

#### Минимальная конфигурация для инференса
- CPU: 4 ядра
- RAM: 8 GB
- GPU: не требуется
- свободное место: не менее 5 GB

#### Рекомендуемая конфигурация
- CPU: 8+ ядер
- RAM: 16 GB
- GPU: NVIDIA с 8+ GB VRAM
- свободное место: 10+ GB

GPU не является обязательным для запуска, но может использоваться для ускорения инференса.

### Данные и модели (опционально)

Исходный датасет и файлы разметки требуются только для воспроизведения
полного цикла обучения или переобучения моделей.

Для обычного запуска готового решения исходный датасет не требуется:
достаточно обученных моделей из каталога `models/`.

Перед запуском необходимо разместить исходные данные и обученные модели в соответствующих каталогах:

```text
DepthZdravHack/
└──data/
    └── raw/
        └── routing_labels_clean.csv

DepthZdravHack/
└──models/
    ├── routing_best.pt
    ├── quality_spine_best.pt
    └── quality_hip_best.pt
```

### Производительность

Время обработки фиксируется для каждого результата в поле
`time_of_processing`.

На целевой конфигурации время обработки одного исследования занимает меньше секунды. Финальная оценка соответствия ограничению ≤3 минут на исследование.

## 5. Обучение моделей (опционально)

**Обучение моделей не требуется для запуска готового решения**. В состав решения включаются предварительно обученные веса моделей, необходимые для работы AI-сервиса.

### 5.1. Подготовка данных для полного цикла обучения

Для полного цикла обучения необходимо разместить исходный датасет исследований в папке:

```text
DepthZdravHack/data/raw/
```
Структура должна содержать исходные DICOM-исследования и файлы разметки, например:

```text
DepthZdravHack
└──data/
    └──raw/
        ├── Исследования/
        │   ├── ...
        │   └── ...
        ├── разметка.xlsx
        └── routing_labels_clean.csv
```

Файл:
```text
DepthZdravHack/data/raw/routing_labels_clean.csv
```

Уже содержит подготовленную разметку анатомической области, поэтому повторно выполнять ручную разметку через build_contact_sheets.py при наличии этого файла не требуется.

### 5.2. Формирование обучающего манифеста

После размещения полного датасета в data/raw/ необходимо сформировать единый обучающий манифест:

```bash
python tools/build_manifest.py \
    DepthZdravHack/data/raw/routing_labels_clean.csv \
    DepthZdravHack/data/raw/разметка.xlsx \
    DepthZdravHack/data/raw/Исследования \
    DepthZdravHack/data/manifest.csv
```

В результате создаётся:

```text
DepthZdravHack/data/manifest.csv
```
Манифест объединяет информацию об анатомической области и экспертной оценке качества исследования и используется последующими скриптами обучения.

### 5.3. Обучение моделей

После формирования `manifest.csv` можно последовательно обучить модели.

**Routing-модель** — определение анатомической области:

```bash
python DepthZdravHack/tools/train_routing.py \
    --manifest DepthZdravHack/data/manifest.csv \
    --epochs 15
```

**Модель качества позвоночника:**

```bash
python DepthZdravHack/tools/train_quality.py \
    --manifest DepthZdravHack/data/manifest.csv \
    --group spine \
    --epochs 20
```

**Модель качества бедра:**

```bash
python DepthZdravHack/tools/train_quality.py \
    --manifest DepthZdravHack/data/manifest.csv \
    --group hip \
    --epochs 20
```

В результате формируются веса:

```text
DepthZdravHack/
└──models/
   ├── routing_best.pt
   ├── quality_spine_best.pt
   └── quality_hip_best.pt
```

### 5.4 Калибровка и проверка

После обучения можно выполнить калибровку порогов:

```bash
python DepthZdravHack/tools/tune_thresholds.py \
    --manifest DepthZdravHack/data/manifest.csv \
    --spine_checkpoint DepthZdravHack/models/quality_spine_best.pt \
    --hip_checkpoint DepthZdravHack/models/quality_hip_best.pt
```


Проверка полного **pipeline**:

```bash
python DepthZdravHack/tools/validate_pipeline.py \
    --manifest DepthZdravHack/data/manifest.csv \
    --routing_checkpoint DepthZdravHack/models/routing_best.pt \
    --spine_checkpoint DepthZdravHack/models/quality_spine_best.pt \
    --hip_checkpoint DepthZdravHack/models/quality_hip_best.pt
```

Таким образом, полный цикл обучения выглядит следующим образом:

```text
Исходный датасет
       ↓
data/raw/
       ↓
routing_labels_clean.csv + разметка.xlsx
       ↓
build_manifest.py
       ↓
data/manifest.csv
       ↓
train_routing.py
train_quality.py
       ↓
models/*.pt
       ↓
tune_thresholds.py
       ↓
validate_pipeline.py
```

**Важно:** полный датасет не требуется для обычного запуска готового решения. Он нужен только пользователю, который хочет самостоятельно воспроизвести или изменить процесс обучения.

## 6. Запуск готового решения

Для обычного использования обучение моделей выполнять не требуется.

В состав решения включаются предварительно обученные модели:

```text
DepthZdravHack/
└──models/
   ├── routing_best.pt
   ├── quality_spine_best.pt
   └── quality_hip_best.pt
```

Они используются готовым Python AI-сервисом при обработке DICOM-исследований.

Для запуска готового решения рекомендуется использовать Docker Compose, который автоматически запускает весь необходимый стек.

### 6.1. Запуск полного решения через Docker

Для запуска необходимо выполнить:

```bash
docker compose build
docker compose up -d
```

Compose запускает следующие сервисы:

- **postgres** — PostgreSQL 16;
- **kafka** — Apache Kafka 3.8.0 в KRaft-режиме;
- **ai-service** — готовый Python AI-сервис на FastAPI;
- **backend-api** — Spring Boot API;
- **backend-worker** — обработчик заданий из Kafka;
- **frontend** — веб-интерфейс Next.js.

Архитектура взаимодействия:

```text
Frontend
    │
    ▼
backend-api
    │
    ├──────────────► PostgreSQL
    │
    ▼
  Kafka
    │
    ▼
backend-worker
    │
    │ HTTP
    ▼
ai-service
(FastAPI + ML models)
```

### 6.2. AI-сервис и обученные модели

Полный стек запускается одним `docker-compose.yml`.

Compose поднимает следующие сервисы:

- `postgres` — PostgreSQL 16;
- `kafka` — Apache Kafka 3.8.0 в KRaft-режиме, без Zookeeper;
- `ai-service` — готовый Python/FastAPI ИИ-модуль;
- `backend-api` — Spring Boot API для пользователей, исследований и загрузки сканов;
- `backend-worker` — Spring Boot worker, обрабатывающий задания из Kafka;
- `frontend` — веб-интерфейс Next.js.

Python AI-сервис запускается внутри контейнера ai-service. FastAPI запускается **автоматически**.

Обученные модели подключаются в контейнер через volume:

```text
./DepthZdravHack/models:/app/models:ro
```

В контейнере они доступны по следующим путям:

```text
/app/models/routing_best.pt
/app/models/quality_spine_best.pt
/app/models/quality_hip_best.pt
```

Переменные окружения:

```text
ROUTING_CHECKPOINT=/app/models/routing_best.pt
SPINE_CHECKPOINT=/app/models/quality_spine_best.pt
HIP_CHECKPOINT=/app/models/quality_hip_best.pt
```

backend-worker обращается к AI-сервису по внутреннему Docker-адресу:

```text
http://ai-service:8000
```

Таким образом:

- **FastAPI** отвечает непосредственно за инференс ИИ;
- **Kafka** используется для асинхронной передачи заданий между `backend-api` и `backend-worker`;
- **PostgreSQL** хранит пользователей, исследования, сканы и состояния обработки;
- **backend-worker** связывает Kafka и Python ИИ-сервис.

### 6.3. База данных

Используется PostgreSQL 16.

Начальная схема базы данных создаётся автоматически при запуске `backend-api` с помощью **Flyway**. Отдельный контейнер или сервис для миграций не требуется: Flyway запускается внутри Spring Boot-приложения до полной готовности `backend-api`.

Основные таблицы:

```text
users
researches
scans
processing_jobs
```

Назначение таблиц:

| Таблица | Назначение |
|---|---|
| `users` | пользователи системы, email, хэш пароля и роль |
| `researches` | исследования, принадлежащие пользователю |
| `processing_jobs` | задания на обработку исследования и их статус |
| `scans` | загруженные DICOM-сканы и результаты ИИ-обработки |

Связи:

```text
users
  │
  └── researches
          │
          ├── scans
          │
          └── processing_jobs
                    │
                    └── scans
```

В `scans` сохраняются, в частности:

```text
study_uid
image_uid
anatomical_region
quality_class
violation_type
comment
processing_status
error_message
time_of_processing
thumbnail_png_b64
```

Миграции применяются автоматически при старте `backend-api`, поэтому ручное создание таблиц перед запуском не требуется.

### 6.4. Порядок запуска

`docker-compose.yml` использует `depends_on` и healthcheck для управления готовностью сервисов.

`backend-api` ожидает готовности PostgreSQL и Kafka.

`backend-worker` должен начинать обработку заданий после готовности PostgreSQL, Kafka и `ai-service`.

Frontend запускается после готовности `backend-api`.

### 6.5. Запуск и проверка

Запуск:

```bash
docker compose build
docker compose up
```

После запуска доступны:

```text
Frontend:    http://localhost:3000
Backend API: http://localhost:8080
AI service:  http://localhost:8000
```

Проверка AI-сервиса:

```text
GET http://localhost:8000/api/health
```

Проверка backend:

```text
GET http://localhost:8080/actuator/health
```

Остановка:

```bash
docker compose down
```

Данные PostgreSQL хранятся в Docker volume `postgres_data`. Данные `backend-api` и `backend-worker` также сохраняются в отдельных volumes.

## 7. API

В системе есть два HTTP-интерфейса с разными назначениями.

### 7.1. Backend API

Основной API приложения реализован на Java/Spring Boot и доступен через порт `8080`.

Он отвечает за:

- регистрацию и авторизацию пользователей;
- JWT-аутентификацию;
- создание и получение исследований;
- загрузку сканов;
- создание заданий на обработку;
- получение статусов обработки.

После загрузки скана `backend-api` сохраняет данные в PostgreSQL и передаёт задание в Kafka. Непосредственно инференс выполняется `backend-worker` через внутренний HTTP-вызов `ai-service`.

### 7.2. AI API

ИИ-модуль реализован на FastAPI и запускается в контейнере `ai-service` на порту `8000`.

Это внутренний API готового Python ИИ-сервиса. Отдельно запускать второй FastAPI или второй экземпляр API не требуется.

Основные endpoints AI-сервиса:


| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/api/process` | Endpoint поддерживает передачу нескольких DICOM-файлов в одном запросе |
| `GET` | `/api/download/{job_id}` | Скачивание результатов последнего batch в XLSX |
| `GET` | `/api/health` | Проверка состояния AI-сервиса |
| `GET` | `/` | Страница AI-сервиса |

### POST `/api/process`

Принимает DICOM-файлы через `multipart/form-data`.

Поле:

```text
files
```

Ответ содержит результаты обработки каждого файла.

Пример:

```json
{
  "job_id": "…",
  "results": [
    {
      "filename": "CR000000.dcm",
      "study_uid": "…",
      "image_uid": "…",
      "anatomical_region": "hip_left",
      "quality_class": 1,
      "violation_type": "rotation_error",
      "comment": "признаки некорректной ротации при позиционировании бедра",
      "processing_status": "Success",
      "error_message": "",
      "time_of_processing": 0.43,
      "thumbnail_png_b64": "…"
    }
  ]
}
```

### GET `/api/health`

Используется для проверки доступности сервиса и загрузки моделей.

### GET `/api/download/{job_id}`

Возвращает результаты пакетной обработки в формате XLSX.

## 8. Формат входных данных

На вход сервис получает DICOM-файлы без разметки.

Один набор данных может содержать несколько изображений/серий в рамках исследования.

Загрузчик DICOM:

- считывает необходимые метаданные;
- нормализует изображение;
- обрабатывает некорректные UID;
- восстанавливает физический масштаб изображения в мм/пиксель по DICOM-параметрам.

Используются `PixelSpacing` / `ImagerPixelSpacing`, а при их отсутствии — информация из `ExposedArea` и размера матрицы.

Согласно заданию, решение не должно зависеть от наличия персональных данных в DICOM-метаданных.

---

## 9. Формат выходных данных

Основной результат пакетной обработки — таблица XLSX/CSV.

Одна строка соответствует одному изображению и одной анатомической области.

| Поле | Формат | Описание |
|---|---|---|
| `path_to_study` | String | Путь к исходному файлу |
| `study_uid` | String | Идентификатор исследования из DICOM |
| `image_uid` | String | Идентификатор изображения из DICOM |
| `anatomical_region` | String | `spine`, `hip_left`, `hip_right` |
| `quality_class` | Integer / пусто | `0` — норма, `1` — нарушение |
| `violation_type` | String | Код или список кодов нарушений |
| `comment` | String | Человекочитаемое описание результата |
| `processing_status` | String | `Success` / `Failure` |
| `time_of_processing` | Float | Время обработки в секундах |

Для случаев с эндопротезом некоторые критерии могут быть неприменимы; это отражается в результате обработки.

### Коды нарушений

Для позвоночника:

```text
incorrect_positioning
axis_tilt_over_5deg
foreign_object_or_artifact
```
Критерий `incorrect_positioning` реализован в pipeline, однако на имеющейся отложенной выборке недостаточно положительных примеров для надёжной оценки его качества.


Для бедра:

```text
rotation_error
roi_incorrect
```

Если выявлено несколько нарушений, они могут быть представлены совместно.

## 10. Модель и методы анализа

### 10.1. Определение анатомической области

Для определения области исследования используется:

**ResNet18**, обученная с использованием transfer learning от ImageNet.

Количество классов:

```text
spine
hip_left
hip_right
```

На отложенной выборке routing-модель показала:

```text
macro-F1 = 1.000
```

### 10.2. Оценка качества

Для оценки качества используются отдельные модели для позвоночника и бедра.

Архитектура:

**ResNet18, multi-label classification**

Для каждого критерия используется отдельный выход модели с сигмоидой.

При обучении используется:

```text
BCEWithLogitsLoss
```

с `pos_weight` для компенсации дисбаланса классов.

### 10.3. Геометрический анализ

Критерии, имеющие измерительную природу, реализованы с помощью классического компьютерного зрения:

- анализ контуров;
- определение центров масс;
- вычисление геометрических параметров;
- оценка расстояний в миллиметрах.

Так реализованы:

```text
axis_tilt_over_5deg
roi_incorrect
```

и детектор эндопротеза.

### 10.4. Предобработка

Общий pipeline:

```text
DICOM
  ↓
извлечение изображения
  ↓
нормализация [0, 1]
  ↓
анатомическая маршрутизация
  ↓
анализ качества
  ↓
геометрия / нейросеть
  ↓
постобработка
  ↓
структурированный результат
```

Для нейросетевых моделей изображение:

- изменяется до размера `224 × 224`;
- преобразуется в диапазон `[0, 1]`;
- реплицируется в 3 канала.

Аугментации ограничены изменениями яркости и контраста. Повороты и сдвиги не используются, поскольку они могут изменять геометрические признаки, являющиеся частью целевой метки.

### 10.5. Постобработка

После получения предсказаний применяются откалиброванные пороги:

```text
DEFAULT_NN_THRESHOLDS
DEFAULT_AXIS_TILT_THRESHOLD_DEGREES
DEFAULT_HIP_ROI_MARGIN_THRESHOLD_MM
```

Пороги калибруются отдельным инструментом:

```text
tools/tune_thresholds.py
```

После этого полный pipeline проверяется с помощью:

```text
tools/validate_pipeline.py
```

## 12. Ограничения решения

Текущая версия имеет следующие ограничения:

### Размер выборки

Набор данных небольшой — около 100 исследований от организатора. Поэтому доверительные интервалы отдельных метрик, особенно для бедра, остаются широкими.

### `incorrect_positioning`

Для этого критерия в валидационной выборке недостаточно положительных примеров для надёжной отдельной оценки ROC-AUC.

### `roi_incorrect`

Геометрический алгоритм оценивает отступ относительно силуэта всей видимой кости. Это является приближением исходного клинического критерия.

### Детектор эндопротеза

Детектор откалиброван на трёх реальных примерах. Используемый порог основан на различии яркостных характеристик, однако размер выборки недостаточен для статистически устойчивой оценки качества этого компонента.

### Отсутствие проекции исследования

Отдельная классификация проекции как самостоятельного выходного поля не реализована. Типичная проекция определяется в рамках соответствующей анатомической области.

## 13. Обработка ошибок

Ошибка обработки отдельного DICOM-файла не должна приводить к остановке всего batch.

При ошибке конкретного файла pipeline формирует результат:

```text
processing_status = Failure
```

и сохраняет текст ошибки.

Примеры:

- повреждённый или некорректный DICOM;
- ошибка чтения изображения;
- невозможность восстановить необходимые параметры;
- невозможность выполнить отдельный критерий анализа.

При этом остальные файлы batch продолжают обрабатываться.

Если физический масштаб изображения невозможно восстановить, критерий `roi_incorrect` не оценивается для данного файла.

Наличие эндопротеза также не считается ошибкой: в этом случае соответствующие критерии помечаются как неприменимые.

## 14. Воспроизводимость

Для воспроизведения результатов необходимо:

1. установить Python и зависимости из `requirements.txt`;

build_manifest.py
        ↓
train_routing.py / train_quality.py
        ↓
tune_thresholds.py
        ↓

### Итог

Решение представляет собой локальный сервис автоматизированного контроля качества DXA-денситометрических исследований.

Основная архитектурная особенность — использование гибридного подхода:

- нейросетевые модели применяются для распознавания визуальных признаков;
- геометрические алгоритмы — для измерительных критериев;
- единый pipeline объединяет результаты различных методов;
- итог предоставляется через CLI, HTTP API и веб-интерфейс.

Система подготовлена для пакетной обработки DICOM-исследований и формирования структурированного результата, пригодного для последующего анализа и проверки.
